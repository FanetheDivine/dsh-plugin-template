# 功能规格：两段访谈与审查门禁

**功能分支**：`feat/019-spec-clarification-review`

**创建日期**：2026-11-19

**状态**：Approved

**输入**：用户描述：「我发现按照spec流程 ai并没有找我澄清需求。加一个类似 /grilling 的需求澄清环节 向用户确认所有实现细节；写好的spec也需要让用户审查。以及输出语言和文档都要和用户所用语言保持一致」

**变更类别**：模板变更

## 待确认决策

无。

## 澄清记录

### 2026-11-19 会话

- 问：需求访谈应确认到哪一层实现细节？ → 答：采用两段访谈和两道批准门禁：规格草稿 → 需求访谈 → 规格批准 → 计划草稿 → 实现细节访谈 → 计划批准 → 任务与实现。
- 问：用户明确要求跳过访谈或审查时，流程应怎样处理？ → 答：记录豁免及未确认风险后继续；Agent 不得自行跳过。
- 问：“文档使用用户语言”的范围应包括哪些文件？ → 用户跳过；该决策随后随“用户语言”需求整体放弃。
- 问：用户在规格或计划批准后切换语言时，应怎样处理已批准文档？ → 答：放弃“用户语言”整个需求，包括语言跟随与文档翻译。
- 问：用户审查规格或计划时，应以什么粒度批准？ → 答：只接受对当前完整版本的批准；部分认可仍需先解决其余意见。
- 用户补充：两段访谈都在 AI 完成探索后进行；不得把“不确定”或“待验证”留到实现阶段。
- 用户补充：每批一次性确认尽可能多的相互独立问题；需要前置答案的问题留到后续批次，不提出依赖未答问题的条件式问题。

## 审查记录

- 2026-11-19：用户明确批准当前完整规格。

## 用户场景与测试

### 用户故事 1 - 每个变更都经过充分的需求澄清（优先级：P1）

用户提出需求后，Agent 建立规格草稿并完成代码库、现有文档与约束探索，再主动访谈用户。规格批准后，Agent 制定计划草稿并完成技术方案探索，再访谈用户确认实现细节。两段访谈都按决策依赖分批推进，直到双方对待建内容与实现方式形成一致理解。

**优先级理由**：未经确认的决策会直接进入计划和实现，导致交付方向偏离用户意图。

**独立测试**：分别提供一个描述完整的需求和一个存在多处空白的需求，观察两种情况下是否都在探索后进入访谈、每批问题是否覆盖当前全部独立决策，以及实现开始时是否没有未决项。

**验收场景**：

1. **Given** 规格草稿没有未决标记，**When** 规格生成阶段结束，**Then** Agent 仍进入需求访谈。
2. **Given** 同时存在多个相互独立的问题，**When** Agent 向用户提问，**Then** 同一批确认全部问题，并分别给出推荐答案。
3. **Given** 一个问题可从代码库得到可靠答案，**When** Agent 准备提问，**Then** Agent 在访谈前检查代码库并自行解决该问题。
4. **Given** 一个问题依赖尚未回答的前置决策，**When** Agent 组织当前批次，**Then** 该问题进入后续批次，当前批次不出现以假设答案为前提的条件式问题。
5. **Given** 用户回答了一个影响后续选择的问题，**When** Agent 组织下一批问题，**Then** 后续问题采用该答案并处理受影响的决策分支。
6. **Given** 需求访谈结束且规格已获批准，**When** 计划草稿与技术探索完成，**Then** Agent 继续分批确认计划中的实现细节。
7. **Given** 任一访谈结束，**When** 检查对应文档与决策记录，**Then** 所有需要用户决定的事项都有明确答案，只有用户豁免的事项可以保留未确认状态。
8. **Given** 实现阶段出现新的不确定项，**When** Agent 继续工作，**Then** Agent 暂停受影响工作，完成探索并返回对应访谈与审查环节。
9. **Given** 用户明确要求跳过任一访谈或审查，**When** Agent 继续流程，**Then** 对应文档记录豁免、未确认事项与风险；Agent 无权自行豁免。

---

### 用户故事 2 - 用户批准规格后才能制定计划（优先级：P1）

访谈结果写回规格后，Agent 请用户审查完整规格。用户明确批准当前版本后，流程才进入计划阶段；用户提出修改时，Agent 更新规格并再次请求审查。

**优先级理由**：规格是后续计划与验收的依据，用户需要确认它准确表达了需求。

**独立测试**：在未批准、要求修改、明确批准和用户明确豁免四种情况下分别尝试进入计划阶段，检查流程是否只在批准或豁免后继续。

**验收场景**：

1. **Given** 需求访谈已结束，**When** 规格已更新，**Then** Agent 向用户提供规格位置和审查要点，并等待明确批准。
2. **Given** 用户要求修改规格，**When** 修改完成，**Then** Agent 再次请求用户审查修改后的完整规格。
3. **Given** 当前规格既没有有效的用户批准记录，也没有用户豁免记录，**When** Agent 准备制定计划，**Then** Agent 停止推进并先完成规格审查。
4. **Given** 已批准规格发生实质变化，**When** Agent 准备制定计划，**Then** 原批准不再适用于新版本。
5. **Given** 用户只认可规格的部分内容，**When** Agent 准备制定计划，**Then** Agent 先解决其余意见并请求对完整版本的批准。

---

### 用户故事 3 - 用户批准计划后才能分解任务（优先级：P1）

计划草稿中的技术方案经过实现细节访谈后，Agent 请用户审查完整计划。用户明确批准当前版本后，流程才进入任务分解；用户提出修改时，Agent 更新计划并再次请求审查。

**优先级理由**：任务会继承计划中的技术决策，用户需要在任务展开前确认实现方式。

**独立测试**：在计划未批准、要求修改、明确批准和用户明确豁免四种情况下分别尝试生成任务，检查流程是否只在批准或豁免后继续。

**验收场景**：

1. **Given** 实现细节访谈已结束，**When** 计划已更新，**Then** Agent 向用户提供计划位置和审查要点，并等待明确批准。
2. **Given** 用户要求修改计划，**When** 修改完成，**Then** Agent 再次请求用户审查修改后的完整计划。
3. **Given** 当前计划既没有有效的用户批准记录，也没有用户豁免记录，**When** Agent 准备分解任务，**Then** Agent 停止推进并先完成计划审查。
4. **Given** 已批准计划发生实质变化，**When** Agent 准备分解任务，**Then** 原批准不再适用于新版本。
5. **Given** 用户只认可计划的部分内容，**When** Agent 准备分解任务，**Then** Agent 先解决其余意见并请求对完整版本的批准。

### 边界情况

- 用户只给出简短需求，大量决策尚未表达。
- 用户连续回答中改变了此前的决定。
- 用户要求暂停访谈或直接跳过审查。
- 用户只批准规格的某一部分。
- 用户在批准后又修改需求。

## 需求

### 功能需求

- **FR-001**：每个变更流程 MUST 执行两段访谈：规格草稿与需求探索后、计划前的需求访谈，以及计划草稿与技术探索后、任务前的实现细节访谈。规格中的未决标记数量不影响需求访谈的执行。
- **FR-002**：Agent MUST 在每段访谈前完成代码库、现有文档、现有接口、依赖与约束的探索，先解决能够可靠自行确定的问题，仅将需要用户决定的问题交给用户。
- **FR-003**：两段访谈 MUST 在每批中一次性提出当前尽可能多的相互独立问题，等待整批回答后继续；每个问题 MUST 附推荐答案与理由。
- **FR-004**：两段访谈 MUST 按决策依赖遍历相关分支。需求访谈覆盖目标、行为、边界、异常、验收、集成与质量要求；实现细节访谈覆盖架构、数据、接口、依赖、失败处理、验证方式与交付风险。访谈不以固定问题数量提前结束。
- **FR-005**：Agent MUST 把每个已接受答案写回对应过程文档，并消除被新答案取代的矛盾内容。
- **FR-006**：Agent MUST 在需求访谈后请求用户审查完整规格，并在收到对当前版本的明确批准或用户对审查的明确豁免后才允许制定计划。
- **FR-007**：规格在批准后发生实质变化时，Agent MUST 使原批准失效并重新请求审查。
- **FR-008**：计划阶段 MUST 检查当前规格具有有效的用户批准或审查豁免记录；缺失或失效时 MUST 返回规格审查环节。
- **FR-009**：需求访谈、实现细节访谈、规格批准、计划批准与用户豁免 MUST 在过程文档中可追溯，供后续会话核验。
- **FR-010**：Agent MUST 在实现细节访谈后请求用户审查完整计划，并在收到对当前版本的明确批准或用户对审查的明确豁免后才允许分解任务。
- **FR-011**：计划在批准后发生实质变化时，Agent MUST 使原批准失效并重新请求审查。
- **FR-012**：任务阶段 MUST 检查当前计划具有有效的用户批准或审查豁免记录；缺失或失效时 MUST 返回计划审查环节。
- **FR-013**：只有用户明确指示才能豁免访谈或审查。Agent MUST 记录豁免阶段、未确认事项与风险，且不得代替用户作出豁免决定。
- **FR-014**：规格与计划的每次批准 MUST 针对当前完整版本。部分认可不构成批准，Agent MUST 先解决其余意见并重新请求完整版本批准。
- **FR-015**：依赖前置答案的问题 MUST 进入后续批次。当前批次 MUST 只包含可以根据已知信息独立回答的问题，条件式问题 MUST 在前置答案确定后改写为具体问题。
- **FR-016**：实现开始前 MUST 解决全部“不确定”“待验证”与其他未决项，用户明确豁免的决策除外。实现阶段发现新未决项时，Agent MUST 暂停受影响工作，完成探索并返回对应访谈与审查环节。

### 关键实体

- **决策项**：一个需要确认的需求或实现选择，包含问题、依赖、推荐答案、用户答案与状态。
- **规格版本**：用户审查的完整规格内容；实质修改后形成需要重新批准的新版本。
- **规格批准**：用户对某一规格版本的明确认可，包含批准时间与适用范围。
- **计划版本**：用户审查的完整计划内容；实质修改后形成需要重新批准的新版本。
- **计划批准**：用户对某一计划版本的明确认可，包含批准时间与适用范围。
- **流程豁免**：用户对某一访谈或审查环节的明确跳过指示，包含豁免阶段、未确认事项与风险。

## 成功标准

### 可衡量结果

- **SC-001**：在规格草稿没有未决标记的测试需求中，需求访谈触发率达到 100%。
- **SC-002**：测试用例中，每批提问覆盖当时全部相互独立的问题，且每个问题都有推荐答案；依赖未答前置决策的问题提前出现次数为 0。
- **SC-003**：测试用例中所有需要用户决定的决策项均有用户答案，代码库与文档可回答的事项均在访谈前通过探索解决。
- **SC-004**：当前规格既未获明确批准也无用户豁免记录时，计划阶段启动次数为 0；批准后发生实质修改时，重新审查触发率达到 100%。
- **SC-005**：现有模板安装、示例工具与质量检查保持可用。
- **SC-006**：当前计划既未获明确批准也无用户豁免记录时，任务阶段启动次数为 0；批准后发生实质修改时，重新审查触发率达到 100%。
- **SC-007**：测试用例中所有实现决策均有用户答案；存在用户豁免时，所有未确认决策均列入豁免记录。
- **SC-008**：Agent 自行跳过访谈或审查的次数为 0；每次用户豁免都有对应的过程记录。
- **SC-009**：仅有部分认可时进入下一阶段的次数为 0，每次推进都有对当前完整版本的批准或用户豁免记录。
- **SC-010**：实现开始时未豁免的未决项数量为 0；实现中新出现的未决项均触发暂停、探索与重新确认。

## 假设

- 需求访谈与实现细节访谈默认都是必经环节，分别发生在需求探索与技术探索之后。用户暂停任一访谈会暂停后续流程，用户明确豁免后可以继续。
- 规格审查与计划审查默认需要用户明确批准，沉默或仅查看文件不算批准，用户明确豁免后可以继续。
- 规格记录需求与约束，实施计划记录技术方案；需要用户确认的实现决策会写入对应文档。
- 用户批准记录保存在对应文档中，后续会话可以据此核验。
