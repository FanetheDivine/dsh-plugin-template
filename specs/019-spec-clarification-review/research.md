# 技术研究：两段访谈与审查门禁

**日期**：2026-11-19
**状态**：实现细节已确认

## 1. 流程承载位置

**决策**：`speckit-clarify` 负责需求探索、需求访谈和规格审查；`speckit-plan` 负责技术探索、实现细节访谈和计划审查；`speckit-tasks` 与 `speckit-implement` 检查文档状态。

**理由**：复用现有 DSH 主流程，无需增加用户命令。

**备选方案**：新增独立审查 skill 会增加流程命令；只修改 `AGENTS.md` 无法覆盖直接调用 skill 的场景。

## 2. 探索与访谈顺序

**决策**：每段访谈前先完成对应探索。需求探索检查代码库、文档、接口和约束；技术探索完成计划、研究、数据与验证设计。未豁免未决项不得进入实现。

**理由**：现有 clarify 只扫描规格文本，plan 没有实现细节访谈和批准门禁。

## 3. 问题分批

**决策**：按决策依赖分层，每批包含当前全部相互独立的问题。每题使用稳定编号并附推荐答案与理由；整批回答后写回文档，再生成下一层。取消固定问题数量上限。

**理由**：独立问题可一次回答，依赖问题需等待前置答案。

**备选方案**：每次一问增加交互轮次；固定最多五题会遗留决策；一次列出整棵树会引入条件式问题。

## 4. 待确认问题与恢复

**决策**：使用文档内 `## 待确认决策` 保存未答问题及依赖，回答后移除并写入澄清记录。用户部分回答时，保留未答项并加入下一批。

**理由**：跨会话可直接恢复，无需重新推断已回答内容。

## 5. 批准与失效

**决策**：状态字段使用 `Draft`、`Approved`、`Waived`，审查记录保存日期、决定、完整文档范围、未确认事项与风险。实质修改后回到 `Draft`，历史记录保留；纯排版修正保持状态。

**理由**：满足可追溯与重新审查要求，无需脚本或内容哈希。

**备选方案**：Node.js 门禁脚本可以自动校验摘要，但超出简单 skill 改造范围；仅对话内批准无法跨会话恢复。

## 6. 入口与范围

**决策**：`AGENTS.md` 将 clarify 改为必做，specify 完成报告固定指向 clarify。修改 `specify`、`clarify`、`plan`、`tasks`、`implement` 五个 skill。外部 workflow 与现有 Bash 脚本保持不变。

**理由**：修正当前“存在不确定项时才澄清”的漏洞，覆盖 DSH 主流程。

## 7. 模板与受管文件

**决策**：spec 与 plan 模板增加状态、待确认决策、澄清记录和审查记录。修改核心 skill 与模板后同步对应 integration manifest 的 SHA-256。

**理由**：核心 skill 没有仓库内渲染源，当前直接修改生成文件并同步清单最直接。

**维护风险**：上游 Spec Kit 刷新可能覆盖本地流程修改，`docs/development.md` 需记录重新应用要求。

## 8. 验证策略

**决策**：只审查文档、模板、manifest 与 diff，并运行仓库既有质量检查；不新增门禁脚本测试，不运行真实宿主验证。

**理由**：用户选择简化范围。真实模型访谈行为留待实际使用验收。
