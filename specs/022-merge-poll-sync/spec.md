## 用户场景与测试

### 用户故事 1 - 合并等待先密集后稀疏 (Priority: P1)

Agent 创建 PR 后等待合并时，前 5 分钟每 10 秒检查一次合并状态，之后改为每 30 秒检查一次。用户合入 PR 后，Agent 在最需要快速响应的窗口内及时感知。

**优先级理由**：前 5 分钟用 10 秒让刚合入的 PR 被尽快发现，之后用 30 秒降低查询频率。

**独立测试**：在一个未合并的 PR 上启动合并等待，记录前 5 分钟与之后的检查间隔；再在 5 分钟内合入 PR，测量从合并到等待结束的延迟。

**验收场景**：

1. **Given** 合并等待刚启动且 PR 未合并，**When** 记录相邻两次检查的时间差，**Then** 时间差约为 10 秒。
2. **Given** 合并等待已持续 5 分钟且 PR 未合并，**When** 记录相邻两次检查的时间差，**Then** 时间差约为 30 秒。
3. **Given** 等待进入 30 秒阶段，**When** PR 在此期间被合并，**Then** 等待在下一个检查点报告合并，延迟不超过 30 秒。
4. **Given** 等待处于 10 秒阶段，**When** 检查发现冲突、评审意见或 PR 关闭，**Then** 等待按原规则报告对应结果。
5. **Given** 等待处于任一阶段，**When** 读取 CI 等待命令，**Then** 检查间隔为 15 秒。

---

### 用户故事 2 - 合并后先同步 main 再清理 (Priority: P1)

Agent 检测到 PR 合并后，先把会话的工作目录切到主工作区，把主工作区整理到可拉取状态，再把 `main` 快进到 `origin/main`，最后才执行删除远程分支、本地分支与 worktree 的清理。放弃模式同样先同步 `main`，再清理。

**优先级理由**：用户要求合并后的本地 `main` 立即可用；清理会删除功能分支与 worktree，先同步可让主工作区在任何清理动作之前反映合并结果。

**独立测试**：在一个 PR 上完成合并等待，观察清理日志顺序与主工作区 `main` 的提交；构造主工作区位于其他分支、存在未提交变更或未推送提交的三种情况，检查同步前的整理结果。

**验收场景**：

1. **Given** 合并等待报告 PR 已合并，**When** Agent 继续交付流程，**Then** 第一个动作是把会话工作目录切到主工作区。
2. **Given** 主工作区有未提交变更，**When** Agent 开始同步，**Then** 变更进入 stash，主工作区恢复干净。
3. **Given** 主工作区位于其他分支，**When** 未提交变更已 stash，**Then** Agent 切回 `main`。
4. **Given** 主工作区有未推送提交，**When** Agent 准备切回 `main`，**Then** 提交先保存在临时分支，`main` 随后快进到 `origin/main`。
5. **Given** 主工作区 `main` 落后于 `origin/main`，**When** 同步成功，**Then** `main` 等于 `origin/main`，随后才运行清理脚本。
6. **Given** 模式为放弃，**When** 用户确认放弃，**Then** Agent 先同步 `main`，再运行清理脚本。
7. **Given** PR 未合并就关闭，**When** 等待报告 `CLOSED`，**Then** Agent 不运行同步与清理。

### 边界情况

- PR 在两次检查之间被合并，检测延迟等于当前轮询间隔。
- 5 分钟边界正好落在两次检查之间，下一轮采用 30 秒间隔。
- CI 等待耗时超过 5 分钟，合并等待的 10 秒阶段从合并等待启动时重新计时。
- 主工作区处于 detached HEAD。
- 主工作区的未提交变更包含未跟踪文件。
- stash 操作失败。
- 本地 `main` 领先 `origin/main`。
- 同步因网络或权限失败。
- 远程分支在合并时被平台自动删除。

## 需求

### 功能需求

- **FR-001**: 合并等待 MUST 在启动后的前 5 分钟按 10 秒间隔检查 PR 状态。
- **FR-002**: 合并等待 MUST 在启动 5 分钟后按 30 秒间隔检查 PR 状态。
- **FR-003**: 每次检查 MUST 先判断合并与关闭状态，再判断冲突与评审意见，合并优先于其他结果。
- **FR-004**: CI 等待 MUST 按 15 秒间隔检查。
- **FR-005**: 检测到 PR 合并后，Agent MUST 先把会话工作目录切到主工作区，再执行任何清理动作。
- **FR-006**: 主工作区有未提交变更时，Agent MUST 先把这些变更存入 stash，再切回 `main`。
- **FR-007**: 主工作区有未推送提交时，Agent MUST 先把这些提交保存在临时分支，再让 `main` 快进到 `origin/main`。
- **FR-008**: 主工作区不在 `main` 时，Agent MUST 在 stash 与临时分支保存完成后切回 `main`。
- **FR-009**: 准备完成后，Agent MUST 运行主工作区同步脚本，把 `main` 快进到 `origin/main`，不产生合并提交。
- **FR-010**: 交付与放弃两种模式 MUST 都在清理前同步 `main`，清理阶段不再执行同步。
- **FR-011**: PR 未合并即关闭时，Agent MUST 不运行同步与清理。
- **FR-012**: 准备或同步失败时，Agent MUST 报告失败原因并继续清理。
- **FR-013**: 输出 MUST 报告同步结果，以及在本次流程中创建的 stash 与临时分支。
- **FR-014**: `AGENTS.md` 的主工作区规则 MUST 写成「只运行 `git fetch`、`git pull` 与可恢复的操作」，并把可恢复定义为不丢失已提交内容与未提交变更。
- **FR-015**: `AGENTS.md` MUST 列出允许的命令：`git fetch`、`git pull`、`git stash`、`git switch`、`git branch`、`git reset --hard`、`git worktree remove`、`git branch -D`；`git reset --hard` 只在目标提交已保存到临时分支时使用。

### 关键实体

- **合并等待**：一个无上限的后台任务，周期性检查 PR 的合并、关闭、冲突与评审状态。
- **PR**：由交付流程创建的拉取请求，等待其被合并。
- **主工作区**：仓库根目录的检出，`main` 分支的同步目标。
- **stash 条目**：保存主工作区未提交变更的本地记录。
- **临时分支**：保存主工作区未推送提交的本地分支。

## 成功标准

### 可衡量的结果

- **SC-001**: 前 5 分钟内相邻两次合并检查的间隔不超过 10 秒。
- **SC-002**: 5 分钟后相邻两次合并检查的间隔不超过 30 秒。
- **SC-003**: CI 检查的间隔为 15 秒。
- **SC-004**: 检测到合并后，主工作区 `main` 在清理 worktree 前等于 `origin/main`。
- **SC-005**: 放弃模式下 `main` 同步发生在清理 worktree 之前。
- **SC-006**: 主工作区存在未提交变更、未推送提交或位于其他分支时，流程仍能完成同步，且不丢失变更与提交。
- **SC-007**: 交付流程的文本产物中不存在旧的固定 30 秒以上轮询表述，也不存在清理后才同步 `main` 的表述。

## 假设

- 主工作区通常位于 `main` 且干净；异常状态按 FR-006 至 FR-008 处理。
- Agent 能运行 `.specify/extensions/worktree/scripts/bash/sync-main.sh`。
- 合并等待使用单个后台任务，检查间隔由循环内部的休眠实现。
- 5 分钟窗口从合并等待启动时起算，不包含 CI 等待耗时。
- stash 与临时分支保留在本地，流程结束后不自动恢复或删除。
- 同步仍失败时按 FR-012 报告并继续清理，主工作区保持原状。
